# STEP 4 — AUTHORITY-BACKED PRODUCTION

**Redefined Problem Statement** — freezes scope and dependencies after 4.Q.1 and 4.Q.2b-1 audit.

---

## What Step 3 Actually Established

Step 3 proved an **execution and measurement loop** for one specific target (Release):

```
intent
  ↓
semantic target (Release)
  ↓
decision (hardcoded: magnitude 0.03, 0.05, or 0.08)
  ↓
real mutation
  ↓
render
  ↓
measure (tail_rms_db)
  ↓
accept/reject
  ↓
episode
```

Supporting evidence:
- Retrieval can influence decision
- Measurements are repeatable and episodic
- Episodes record authority state and decision rationale

**But all surrounding infrastructure was target-specific scaffolding:**
- Planner hardcodes Release scope: `[0.50, 0.80]`
- Planner hardcodes current value: `0.50`
- Planner hardcodes magnitude steps: `[0.03, 0.05, 0.08]`
- CapabilityContract was mocked, not loaded
- Admission was bypassed

**Therefore:** Step 3 did NOT establish a generalized production mechanism. It established a loop for one specific target with hardcoded authority.

---

## What Step 4 Must Prove

Step 4 is NOT about:
- Making Release work with a real contract (that is substep 4.1)
- Building multi-value candidate grids (that is extension 4.3)
- Generalizing context ranges (that is extension 4.4)
- Adding Detune support (that is step 4.5)

Step 4 IS about proving:

```
┌─────────────────────────────────────────────────────┐
│ Can this system turn human intent into measured     │
│ execution WITHOUT target-specific authority bypass? │
└─────────────────────────────────────────────────────┘
```

Specifically:

1. **Authority Substrate Proof (4.1):** A single real capability contract is loaded, context is verified at runtime, admission gates pass/refuse based on actual evidence, live state is read, an **admissible action is generated by generic policy** (not hardcoded for the target), execution proceeds, measurement occurs, episode is recorded. No target-specific hardcoding anywhere in the authority or decision path.

2. **Target-Independence Proof (4.2):** A second independently qualified Serum capability executes through the identical authority/runtime/decision pathway with zero target-specific authority logic. No Release-specific planner branch, no Attack-specific defaults, no Detune-specific workarounds.

---

## Why Multi-Value Authority Is Not Step 4

The candidate-grid debate became central because Step 3 happened to use a magnitude grid.

But the **deeper architectural question** is:

```
Can authority constrain what decisions are admissible?
```

That is orthogonal to whether authority contains one mutation value or ten.

Current architecture fails this because:

```
CapabilityContract (authority)
  ↓
does NOT constrain candidate values
  ↓
planner can invent candidate outside tested scope
  ↓
admission does NOT validate candidate against scope
  ↓
execution proceeds unvalidated
```

This hole exists whether authority is singleton or multi-value.

**Fix required:** Authority must gate admissible candidates at decision time, not hope admission will catch them later.

But **extending authority to multi-value** is a separate extension (4.3) from **proving authority gates decisions** (4.1–4.2).

Do not build multi-value authority to prove the substrate works. Prove the substrate works first, then extend it.

---

## Why Release, Then Attack (Not Attack, Then Detune)

**Release:** Has historical CAUSAL_VERIFIED contract. Problem is context incompleteness (Decay=0.02 not captured in old schema). Requalifying Release with complete context demonstrates how to build an authority artifact from scratch.

**Attack:** Also has historical CAUSAL_VERIFIED contract. Can be requalified with complete context. More importantly: proves the identical runtime path handles a different target without releasing the Release-specific hardcoding. This is the **generalization proof**.

**Detune:** Currently has no authority. Qualifies only after Attack proves the substrate is target-independent. Then Detune becomes: "new capability qualification" not "proof that the substrate works."

### **4.1 — Authority Substrate Proof**

**Objective:** Demonstrate one real authority-backed vertical slice by establishing fresh Release authority through independent qualification and proving it gates runtime execution.

**What this phase proves:**
- A fresh CapabilityContract can be built from new evidence (not reused from archive)
- Context prerequisites can be captured and verified at runtime
- Admission gates enforce causal + prerequisite requirements with refusal power
- If admission refuses, execution does NOT proceed
- If admission passes, a generic decision policy produces an admissible action
- Execution, measurement, and episode recording work without target-specific hardcoding
- Both PASS and REFUSED pathways function as specified

**What this phase does NOT prove:**
- Multi-value candidate grids work
- The mechanism generalizes to other targets (that is 4.2)
- Context ranges or generalization across conditions

**Acceptance criteria:**
- [ ] Fresh Release EvidenceRecord generated with complete context provenance (Decay=0.02 from live readback)
- [ ] New CapabilityContract built from fresh evidence
- [ ] Causal outcome determined by independent measurement (EFFECT_OBSERVED vs NO_OBSERVED_EFFECT)
- [ ] If measurement shows EFFECT_OBSERVED: contract.status becomes CAUSAL_VERIFIED; proceed to execution demonstration
- [ ] If measurement shows NO_OBSERVED_EFFECT: contract.status becomes NEGATIVE_EVIDENCE; 4.1 FAILS, stop, do not reuse archived contract
- [ ] N=1 PASS demonstration: Admission passes, context verified, mutation executes, measurement recorded, episode published
- [ ] N=1 BLOCKED demonstration: Admission refuses (intentional context mismatch), mutation does NOT execute, BLOCKED episode recorded
- [ ] No Release-specific hardcoding in planner or decision path

**Deliverables:**
- serum2/qualification/release_qualified_complete_004_EVIDENCE.json (EvidenceRecord)
- experiments/_capability_contracts_4_1.pkl (fresh contract)
- serum2/qualification/release_qualified_complete_004_PASS.json (N=1 PASS episode)
- serum2/qualification/release_qualified_complete_004_BLOCKED.json (N=1 BLOCKED episode)

### **4.2 — Target-Independence Proof**

**Objective:** Execute a second capability through the identical authority pathway without any target-specific logic.

**Choice:** Attack or Detune (depends on whether it has a qualified contract)

If Attack is chosen:
- Requalify Attack with complete context provenance
- Load Contract via same admission path
- Use same generic decision policy (NOT Attack-specific hardcoding)
- Same planner architecture (NOT Attack-specific scope/magnitude branch)
- Execute, measure, record

**What this proves:**
- The authority substrate is not Release-specific
- Same runtime path handles different targets
- Generic policy is actually generic

**What this does NOT prove:**
- It scales to N targets (one second target is not enough for generalization claim, but it disproves the false claim "this only works for Release")
- Multi-value authority is needed

**Acceptance criteria:**
- [ ] Second target requalified (Attack or other)
- [ ] Same admission interface used
- [ ] Same planner path (no target-specific branch)
- [ ] One demonstration episode runs
- [ ] Admission passes, execution succeeds
- [ ] No Release-specific hardcoding in the path

**Deliverable:** serum2/qualification/attack_qualified_complete_004.json (or other target) (episode)

## What Cannot Be Skipped

1. **Release context provenance.** The archived contract lacks it. A new qualification must capture baseline_overrides or equivalent.

2. **Admission enforcement.** If admission succeeds, execution must proceed. If it refuses, execution must NOT proceed. No fallback, no bypass.

3. **No Release-specific planner logic in 4.1's decision path.** The candidate must come from generic policy, not hardcoded Release-specific scope/magnitude/current_value.

4. **A second target for 4.2.** Proves substrate is not Release-specific.

---

## What Must Be Rejected

1. **Proving generalization from one target.** 4.1 (Release alone) proves the substrate; 4.2 (Attack) proves it is not Release-specific. Not the same thing.

2. **Inventing context from design documents.** Authority must come from evidence provenance, not inference from documents.

3. **Skipping 4.2.** One target with hardcoding removed is not proof of generalization. A second target exercising the same path is.

4. **Conflating extensions with substrate proof.** Multi-value authority (4.3) and context ranges (4.4) are valuable but separate from proving the substrate works (4.1–4.2).
